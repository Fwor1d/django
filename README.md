## Аннотация

В рамках практических работ № 3–15 последовательно разработано веб-приложение на Python и Django. Начальный проект с тремя статическими страницами был расширен до блога с базой данных, публикациями, комментариями, поиском, постраничным выводом, регистрацией и аутентификацией пользователей, личными профилями и адаптивным интерфейсом.

**Важно:** репозиторий содержит исходный код, а не публично развёрнутый сайт. Приложение запускается локально с помощью сервера разработки Django. Файл базы данных, локальный секретный ключ и пользовательские аватары исключены из Git.

## Практическая работа № 4. Шаблоны и наследование

**Цель:** отделить HTML от Python-кода и освоить повторное использование разметки.

**Выполнено.** Создан общий шаблон `blog/templates/blog/base.html` с блоками `title` и `content`. Дочерние страницы наследуют его через `{% extends 'blog/base.html' %}` и переопределяют содержимое через `{% block %}`. Вместо HTML-строк представления вызывают `render(request, template, context)`.

При `APP_DIRS=True` Django ищет шаблоны в папках `templates` установленных приложений. Если дочерний шаблон не переопределяет блок, используется содержимое родительского блока.

## Практическая работа № 6. ORM, модели, миграции и административная панель

**Цель:** освоить хранение данных в реляционной базе через Django ORM.

**Выполнено.** В `blog/models.py` создана модель `Post` с полями заголовка, текста, краткого описания, даты создания и изменения, признака публикации, автора и slug. Добавлена миграция `blog/migrations/0001_initial.py`. Модель зарегистрирована в Django admin с поиском и фильтрами. Список публикаций получает данные из базы вместо жёстко записанных HTML-элементов.

QuerySet описывает выборку данных. `makemigrations` создаёт миграции по изменениям моделей, `migrate` применяет их к базе. ## Практическая работа № 7. Динамические URL и детальная страница

**Цель:** научиться открывать отдельный объект по параметру URL и обрабатывать отсутствие записи.

**Выполнено.** Реализовано представление отдельного поста, получение объекта через `get_object_or_404` и ссылка «Читать далее» из списка. В итоговой версии детальный адрес использует дату и slug; для старого числового пути `/blog/<pk>/` предусмотрено постоянное перенаправление на актуальный URL.

**Основные файлы:** `blog/urls.py`, `blog/views.py`, `post_detail.html`, `post_list.html`.

**Теоретические выводы.** Динамические URL передают переменные в view: например, `<int:pk>` — числовой первичный ключ записи. `get_object_or_404` возвращает объект либо выдаёт HTTP 404, если он не найден; это удобнее необработанного исключения `DoesNotExist`. Использование именованных маршрутов и `reverse` защищает код от жёсткой привязки к конкретной строке адреса. Slug удобнее для чтения, а `pk` проще и надёжнее в качестве внутреннего идентификатора.

**Результат:** у каждой публикации есть отдельная страница; несуществующая запись не вызывает ошибку сервера 500.

**Материалы для отчёта:** список постов, детальная страница, ответ 404 по несуществующему адресу.

## Практическая работа № 8. Формы и CRUD

**Цель:** реализовать создание, чтение, обновление и удаление записей средствами Django.

**Выполнено.** Создана форма `PostForm` на основе `ModelForm`. Представления `post_create`, `post_edit` и `post_delete` обрабатывают GET и POST. Форма создания использует `post_form.html`, а для редактирования предусмотрен отдельный `post_form_edit.html`, наследующий общий шаблон формы; режим определяется переменной `editing`. Удаление выполняется только после подтверждения и отправки POST-запроса.

**Основные файлы:** `blog/forms.py`, `blog/views.py`, `post_form.html`, `post_confirm_delete.html`.

**Теоретические выводы.** `ModelForm` создаёт поля и правила проверки на основе модели, сокращая дублирование. GET предназначен прежде всего для получения формы и просмотра данных, POST — для изменения состояния сервера. `is_valid()` проверяет входные данные. `instance=post` позволяет редактировать существующий объект; `save(commit=False)` — дополнить его полями, например текущим автором, до сохранения. `{% csrf_token %}` защищает отправку форм от CSRF.

**Результат:** пользователь, прошедший аутентификацию, может создать пост и управлять своими публикациями.

**Материалы для отчёта:** пустая форма создания, сохранённый пост, форма редактирования с данными и подтверждение удаления.

## Практическая работа № 9. Комментарии к постам

**Цель:** научиться создавать связанные записи и отображать их на странице родительского объекта.

**Выполнено.** Модель `Comment` связана с `Post` через `ForeignKey` с `related_name='comments'`. В ней хранятся текст, автор-пользователь и дата создания. Форма `CommentForm` обрабатывается на детальной странице; комментарий связывается с постом и авторизованным пользователем. Отображаются список комментариев и их количество.

**Основные файлы:** `blog/models.py`, `blog/forms.py`, `blog/views.py`, `post_detail.html`.

**Теоретические выводы.** Связь «один ко многим» означает, что одному посту может принадлежать множество комментариев. `on_delete=models.CASCADE` удаляет дочерние комментарии при удалении поста. `post.comments.all()` обращается к комментариям через обратную связь. `form.save(commit=False)` позволяет назначить `post` и `author` до записи в БД.

**Результат:** зарегистрированные пользователи оставляют комментарии под публикациями, а неавторизованные перенаправляются на вход.

**Материалы для отчёта:** детальная страница до и после отправки комментария, отображение автора и счётчика.

## Практическая работа № 10. Поиск и пагинация

**Цель:** реализовать фильтрацию QuerySet и разбиение результатов на страницы.

**Выполнено.** Добавлена GET-форма поиска с параметром `q`. Запрос ищет совпадения по заголовку, тексту и краткому описанию посредством `Q` и `icontains`. Для списка используется `Paginator(posts, 5)`. В ссылках перехода между страницами сохраняется поисковая строка. Для некорректных номеров страниц используется `get_page`, который не приводит к необработанному исключению.

**Основные файлы:** `blog/views.py`, `post_list.html`.

**Пример фильтрации:**

```python
posts.filter(
    Q(title__icontains=query)
    | Q(body__icontains=query)
    | Q(summary__icontains=query)
)
```

**Теоретические выводы.** Оператор `|` между объектами `Q` означает логическое «ИЛИ». `icontains` выполняет поиск подстроки без учёта регистра. QuerySet представляет полный запрос к БД, а `Page` — только выбранную часть результатов вместе с информацией о предыдущей и следующей страницах. Сохранение параметра `q` важно, чтобы поиск не сбрасывался при перелистывании.

**Результат:** публикации выводятся по пять на страницу, одновременно работают поиск и пагинация. Для демонстрации добавлена команда `seed_blog_demo`, создающая 12 учебных постов без повторного добавления уже существующих.

**Замечание:** ранее встречалось предупреждение `UnorderedObjectListWarning`. Теперь перед созданием `Paginator` QuerySet явно сортируется по `-created_at` и `-pk`; после этой правки требуется повторный запуск тестов.

**Материалы для отчёта:** список, поисковый результат, переключение страниц с сохранённым запросом.

## Практическая работа № 11. Аутентификация и права доступа

**Цель:** освоить стандартную систему пользователей Django и разграничение прав на изменения данных.

**Выполнено.** Подключены стандартные auth-маршруты. Реализованы регистрация, вход и выход. У поста и комментария есть ссылка на пользовательскую модель. Создание публикаций требует входа в аккаунт; изменение и удаление чужих постов запрещено. На страницах показаны авторы записей и комментариев.

**Основные файлы:** `mysite/urls.py`, `blog/models.py`, `blog/views.py`, шаблоны из `accounts/templates/registration/`.

**Теоретические выводы.** Аутентификация отвечает на вопрос «кто пользователь», авторизация — «что ему разрешено». `@login_required` ограничивает доступ к представлению, но для редактирования чужих объектов необходима дополнительная проверка владельца. `request.user` содержит текущего пользователя. Ошибка 403 используется при недостаточных правах, а 404 — когда объект недоступен или отсутствует.

**Результат:** защищены операции изменения постов и добавления комментариев, в интерфейсе отражён статус входа.

**Материалы для отчёта:** регистрация, вход, интерфейс авторизованного пользователя, попытка редактирования чужой публикации.

## Практическая работа № 15. Маршрутизация, slug и канонические URL

**Цель:** улучшить структуру URL и адреса страниц публикаций.

**Выполнено.** Маршруты постов размещены в `blog/urls.py` и получают пространство имён `blog`. Модель `Post` содержит уникальное поле `slug`, которое формируется автоматически, в том числе для кириллических заголовков с помощью транслитерации. При совпадении значений добавляется числовой суффикс. Метод `get_absolute_url()` формирует ссылку с годом, месяцем, днём и slug; аналогично реализованы ссылки редактирования и удаления. Детальная страница содержит HTML-тег `rel="canonical"`. Старые числовые адреса перенаправляются на канонический URL.

**Пример адреса:** `/blog/2026/10/30/znakomstvo-s-django/`.

**Основные файлы:** `blog/models.py`, `blog/urls.py`, `mysite/urls.py`, `blog/views.py`, `post_detail.html`.

**Теоретические выводы.** Slug — человекочитаемый сегмент адреса, удобный для пользователя и поисковых систем. Канонический URL указывает предпочтительный адрес страницы при наличии альтернативных ссылок. `reverse('blog:post_detail', kwargs=...)` строит URL по имени маршрута и параметрам, а namespace позволяет избежать совпадения имён в разных приложениях. Дата в URL дополнительно описывает публикацию.

**Особенность реализации:** все маршруты самого блога, включая `/`, `/about/` и `/blog/`, определены в `blog/urls.py`; корневой `mysite/urls.py` подключает их через `include('blog.urls')`. Для ссылок на главную и «О проекте» теперь также используются `blog:home` и `blog:about`.

**Результат:** посты имеют стабильные информативные ссылки, а старые адреса не обрываются без перехода.

**Материалы для отчёта:** ссылка поста с датой/slug, HTML-тег canonical, `blog/urls.py`, переход со старого `/blog/<pk>/`.

## 4. Структура базы данных и связи

В проекте используется SQLite и три основные сущности предметной области.

| Модель | Ключевые поля | Связи |
|---|---|---|
| `Post` | `title`, `summary`, `body`, `slug`, `created_at`, `updated_at`, `is_published` | `author` — внешний ключ на пользователя |
| `Comment` | `text`, `created_at` | `post` — внешний ключ на `Post`; `author` — на пользователя |
| `Profile` | `bio`, `location`, `birth_date`, `avatar` | `user` — связь «один к одному» с пользователем |

**Логика связей:** один пользователь может иметь несколько постов и комментариев; один пост — несколько комментариев; одному пользователю соответствует один профиль. При удалении поста его комментарии удаляются каскадно.

Отдельное приложение `university` сохранено в проекте как результат предыдущих учебных работ; его структура и существующие данные не затрагивались при развитии блога.

## 5. Обработка запросов и права доступа

Пример последовательности при открытии поста:

1. Браузер запрашивает адрес вида `/blog/2026/10/30/znakomstvo-s-django/`.
2. `mysite/urls.py` передаёт обработку приложению `blog`.
3. `blog/urls.py` сопоставляет URL с представлением `post_detail`.
4. `views.py` запрашивает публикацию из БД через ORM, проверяет доступность и получает комментарии.
5. `render()` формирует HTML из `post_detail.html` и общего `base.html`.
6. Сервер отправляет HTTP-ответ браузеру.

Доступ к изменению публикаций проверяется отдельно от факта входа: пользователь не должен редактировать или удалять пост другого автора. Суперпользователь имеет дополнительные разрешения. Отправка форм сопровождается CSRF-защитой.

## 6. Установка и запуск на macOS

Порядок предназначен для запуска проекта после `git clone` или загрузки исходников. Требуется установленный Python 3.10+; рабочая версия разработчика — Python 3.11.

### 6.1. Получение проекта

```bash
git clone https://github.com/Fwor1d/django.git
cd django
```

### 6.2. Виртуальное окружение и библиотеки

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

### 6.3. Локальный секретный ключ

В публичный Git не загружается файл `.django-secret-key`. На новом устройстве необходимо сгенерировать локальный ключ:

```bash
python -c 'from pathlib import Path; from django.core.management.utils import get_random_secret_key; Path(".django-secret-key").write_text(get_random_secret_key())'
```

Команда создаёт локальный файл, который уже указан в `.gitignore`. Не публикуйте ключ в GitHub.

### 6.4. Миграции и пользователь администратора

```bash
python manage.py check
python manage.py migrate
python manage.py createsuperuser
```

Миграции создадут таблицы из включённых в репозиторий файлов миграций. Команда `createsuperuser` создаёт администратора для входа в `/admin/`.

### 6.5. Демонстрационные данные и сервер

```bash
python manage.py seed_blog_demo
python manage.py runserver
```

Команда `seed_blog_demo` создаёт до 12 учебных записей, если они ещё не существуют. Для неё нужен хотя бы один пользователь, поэтому она выполняется после создания администратора либо регистрации пользователя. При повторном запуске существующие демонстрационные записи не дублируются по заголовку.

Локальная главная страница: http://127.0.0.1:8000/

Для остановки сервера нажмите `Ctrl+C`.

### 6.6. Если проект уже установлен в ~/django_practice/mysite

Для ранее настроенного MacBook можно использовать существующее окружение:

```bash
cd ~/django_practice
source .venv/bin/activate
cd mysite
python manage.py check
python manage.py runserver
```

**Примечание:** `DEBUG=True` и локальный сервер `runserver` предназначены для разработки, не для публикации в интернете. Для производственного развёртывания необходимо отдельно настроить хосты, секреты, БД, сборку статики, HTTPS, сервер приложений и отправку почты.

## 9. Трудности и способы решения

| Проблема | Причина | Принятое решение |
|---|---|---|
| Команда `python` не найдена в новом терминале | Не активировано Python-окружение; macOS может использовать `python3` | Активировать `.venv`, затем работать через `python` |
| Ошибка `fields.E210` для `ImageField` | Отсутствовала библиотека Pillow | Установлена Pillow, после чего `check` и `migrate` прошли |
| Не выполнялись миграции | Проверка проекта прерывалась на отсутствии Pillow | После установки зависимости применены миграции `accounts` и `blog` |
| Слишком крупный аватар | Изображение выводилось без ограничений на размер | В `profile.html` установлен квадратный размер 140 × 140, округление и `object-fit: cover` |
| Предупреждение пагинации | QuerySet перед `Paginator` рассматривался как неупорядоченный | Рекомендовано явно сортировать результат по `-created_at` и `-pk` |
| FAQ не открывает отдельную страницу | Это дополнительная ссылка-заглушка из ПЗ №5 | Оставлена как необязательный учебный элемент |
| `/favicon.ico` возвращает 404 | Не задан favicon для браузера | На функциональность практических не влияет; можно добавить отдельно |
| Git push был отклонён | В удалённом репозитории уже существовал коммит с `LICENSE` | Истории объединены через `git merge --allow-unrelated-histories` без принудительной перезаписи |
